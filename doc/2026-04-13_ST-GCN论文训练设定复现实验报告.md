# ST-GCN NTU RGB+D xsub 论文训练设定复现实验报告

## 1. 报告目的

本报告记录的是一次面向 ST-GCN 论文训练设定的复现实验，而不是单纯比较“仓库默认配置”和“另一组更好配置”的优劣。

当前关注的问题是：

1. 在本仓库 `modern` 分支和当前正式训练数据产物下，按论文训练节奏组织的学习率日程能否稳定复现出更接近论文预期的结果。
2. 现有仓库默认训练配置与这次“论文训练设定复现”之间，具体差在什么地方。
3. 这次复现结果应如何被后续复查、复画和继续扩展。

## 2. ST-GCN 官方仓库与本次复现的关系

### 2.1 官方仓库默认训练配置

当前仓库自带的 [config/st_gcn/ntu-xsub/train.yaml](../config/st_gcn/ntu-xsub/train.yaml) 仍保留官方实现的默认训练入口，核心参数为：

- `num_epoch: 80`
- `base_lr: 0.1`
- `step: [10, 50]`
- `device: [0, 1, 2, 3]`
- `batch_size: 64`
- `test_batch_size: 64`

因此，仓库自带 `train.yaml` 更适合被理解为“官方实现默认训练配置”，而不是“本次单卡正式复现直接照搬的最终命令”。

### 2.2 本次正式训练的复现方式

本次两组正式训练都运行在单卡、`batch_size=16`、`base_lr=0.025` 的缩放设定下，保持：

- 模型结构不变
- 数据集不变
- 训练总轮数不变
- 评估间隔不变

只有学习率衰减日程不同：

| 运行标签 | 工作目录 | 训练定位 | step |
| --- | --- | --- | --- |
| Repo Default | `work_dir/recognition/ntu-xsub/ST_GCN_fp32_bs16_lr0025_e80` | 仓库默认训练节奏的单卡缩放对照 | `[10, 50]` |
| Paper Schedule | `work_dir/recognition/ntu-xsub/ST_GCN_fp32_bs16_lr0025_e80_step10x` | 论文训练设定复现方向的单卡缩放版本 | `[10, 20, 30, 40, 50, 60, 70]` |

这里需要明确区分两件事：

- `Repo Default` 不是“错误配置”，它是当前官方仓库默认训练节奏在单卡条件下的对照实现。
- `Paper Schedule` 也不是“整篇论文命令的原样抄写”，它是保持当前单卡正式训练前提不变，只把学习率衰减节奏切换到论文复现方向后的正式运行结果。

换句话说，这次实验的真实问题是：

> 在当前单卡正式训练约束下，把学习率衰减从仓库默认的 `[10, 50]` 改为论文复现方向的多次衰减节奏后，结果会发生什么变化。

## 3. 实验设置

两组正式训练共同使用以下条件：

- 数据集：NTU RGB+D xsub
- 模型：`net.st_gcn.Model`
- 训练轮数：`80`
- 初始学习率：`0.025`
- `batch_size: 16`
- `test_batch_size: 16`
- `save_interval: 10`
- `eval_interval: 5`
- 基础配置来源：`config/st_gcn/ntu-xsub/train.yaml`

两组训练对应的实际命令已写入各自 `config.yaml` 头部，可直接回查：

- [work_dir/recognition/ntu-xsub/ST_GCN_fp32_bs16_lr0025_e80/config.yaml](../work_dir/recognition/ntu-xsub/ST_GCN_fp32_bs16_lr0025_e80/config.yaml)
- [work_dir/recognition/ntu-xsub/ST_GCN_fp32_bs16_lr0025_e80_step10x/config.yaml](../work_dir/recognition/ntu-xsub/ST_GCN_fp32_bs16_lr0025_e80_step10x/config.yaml)

## 4. 结果

### 4.1 最终指标

| 运行标签 | Final Top-1 | Final Top-5 | Best Top-1 | Best Top-5 |
| --- | --- | --- | --- | --- |
| Repo Default | `78.75%` | `96.32%` | `78.98%` | `96.39%` |
| Paper Schedule | `79.90%` | `96.73%` | `80.14%` | `96.76%` |

如果把 `Repo Default` 视为当前单卡正式训练下的对照项，那么“论文训练设定复现方向”的这组运行带来的变化是：

- Final Top-1：`+1.15`
- Final Top-5：`+0.41`
- Best Top-1：`+1.16`
- Best Top-5：`+0.37`

### 4.2 如何理解这组结果

这组结果更适合被表述为：

- 在当前 `modern` 分支和当前单卡正式训练设定下，采用论文复现方向的学习率衰减节奏，能够得到更高的 NTU RGB+D xsub 指标。
- 因此，当前仓库默认的 `[10, 50]` 训练节奏并不等于“最接近本次论文复现目标的配置”。
- 这并不自动推出“论文只差一个 step 列表”，因为当前正式训练仍然带有单卡缩放前提，和官方默认 `4 GPU / batch 64 / lr 0.1` 配置并不完全同构。

报告里必须保留这层边界，否则很容易把“当前正式训练下的复现结论”误写成“对原论文训练配方的完整定论”。

### 4.3 后半程无提升的已确认原因

从当前日志和实现细节对齐后，可以确认一个非常直接的现象：

- `processor/recognition.py` 中的学习率调度逻辑沿用官方实现，每命中一个 `step` 就把学习率乘以 `0.1`。
- 因此在当前 `base_lr=0.025`、`step=[10, 20, 30, 40, 50, 60, 70]` 的“Paper Schedule” 运行里，实际学习率会变成：

| epoch 区间 | 实际 lr |
| --- | --- |
| 1-10 | `2.5e-2` |
| 11-20 | `2.5e-3` |
| 21-30 | `2.5e-4` |
| 31-40 | `2.5e-5` |
| 41-50 | `2.5e-6` |
| 51-60 | `2.5e-7` |
| 61-70 | `2.5e-8` |
| 71-80 | `2.5e-9` |

这意味着从 40 轮以后，优化器已经接近“冻结”状态；从 50 轮以后，学习率基本低到只剩形式上的更新。

这和日志中的曲线完全对得上：

- `Paper Schedule` 的最佳 Top-1 出现在 `epoch 45`，为 `80.14%`。
- 之后到 `epoch 80`，验证 Top-1 只是在 `79.79%` 到 `80.03%` 之间小幅波动。
- 与此同时，训练均值 loss 在后 20 轮基本稳定在 `0.417` 到 `0.421` 区间，没有继续形成有效下降趋势。

所以，“后半程无提升甚至轻微回落”的最直接原因并不是未知，而是当前这组 `step10x` 在现有 `gamma=0.1` 实现下衰减得过于激进。

### 4.4 仍然未知的部分

即便把后半程 plateau 的原因解释清楚，当前结果距离旧 README 中给出的 ST-GCN NTU xsub 参考值 `81.6%` 仍然还有约 `1.46` 个百分点差距。这部分目前还不能简单归因到单一因素。

当前更稳妥的说法是：

- 已确认：后半程学不动，主要由过于激进的多次 `0.1` 衰减导致。
- 尚未确认：为什么在 `epoch 45` 已经达到当前最优后，最好值仍停在 `80.14%`，而没有进一步接近 `81.6%`。

需要额外强调的一点是：当前采用的单卡缩放设定，确实会带来与官方默认 `4 GPU / batch 64 / lr 0.1` 不完全一致的训练动力学，但仅凭“缩小到四分之一”本身，还不足以自然解释整整 `1.46` 个点的剩余差距。也就是说，单卡缩放可以解释一部分差异，但大概率不是全部原因。

剩余差距更可能来自多种因素叠加，例如：

- 当前正式训练采用的是单卡缩放配置，而不是官方默认 `4 GPU / batch 64 / lr 0.1` 训练入口。
- 当前“Paper Schedule” 复现的是学习率衰减节奏，而不等于对论文完整训练配方的逐项照搬。
- 旧 README 中给出的 `81.6%` 是最终模型结果，但当前环境下还没有完成“官方预训练权重在当前数据和当前代码上的端到端复测”，因此还缺少一次把数据链路、实现链路和评测链路完全锁死的对照。

## 8. 结论与边界

当前最稳妥的结论是：

- 在这次单卡正式训练约束下，论文训练设定复现方向的学习率日程，相比仓库默认训练节奏，能够带来更好的 NTU RGB+D xsub 结果。
- 当前仓库默认 `train.yaml` 适合作为官方实现默认训练入口，不应直接等同于“本次论文复现目标的最佳配置”。
- 后半程 plateau 的直接原因已经确认，主要是多次 `0.1` 衰减导致学习率过早接近冻结。
- 但离 `81.6%` 仍有约 `1.46` 个点的剩余差距，这部分原因目前还没有完全锁定。
